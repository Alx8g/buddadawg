# Buddadawg OSS release plan

Status: draft, 2026-11-12. Reflects the uncommitted v0.2.0 tree on disk
(`CFBundleShortVersionString 0.2.0`, `CFBundleVersion 2`, bundle id
`co.alex.buddadawg`, generated by `scripts/bundle.sh`). Nothing in this plan
requires reverting v0.2.0; several items require deciding how to ship it
without changing what it does.

Scope: a free, open-source, notarised direct download (plus optional
Homebrew cask) for macOS 15+ on Apple silicon. Paid/commercial blockers are
flagged separately in §11; do not read "free OSS can ship" as "paid can
ship".

### Recommended licence for the app code (#1)

MIT or Apache-2.0. Apache-2.0 matches FluidAudio, adds an express patent
grant, and its `NOTICE` mechanics line up with the attribution stack above;
MIT is simpler. Either is compatible with bundling Apache-2.0 code and
CC-BY(-NC) weights *as separate works* — the repo licence must state
explicitly that it covers the Swift code only and that model weights keep
their own licences. Do not pick GPL for the app code: it would not help the
weights problem and would complicate a future paid build.

Whatever is chosen: add `LICENSE`, keep model `NOTICE`s, and add a single
`THIRD-PARTY-NOTICES.md` (also copied into `Contents/Resources/` by the
future release script) consolidating rows 2–9. Today `bundle.sh` copies
only the root `NOTICE` (Bark verbatim); `ModelsClean/NOTICE` rides along
inside `ModelsClean/`, and the FluidAudio/Nemo notices ship nowhere.

### 1.1 The Conway CC-BY vs CC-BY-NC ambiguity — precise statement

What can be documented today, with sources:

1. The two `NOTICE` files on disk (repo root `NOTICE`, fetched from
   `ConwayResearch/Underdog-Bark-3.0`; `ModelsClean/NOTICE`, fetched from
   `FluidInference/bark-3.0-coreml`) are byte-identical in substance: they
   name NVIDIA Parakeet + Moondream Parakeet Ultra as CC-BY-4.0 upstreams
   and give "License: https://creativecommons.org/licenses/by/4.0/".
2. The live Hugging Face cards for both
   [`ConwayResearch/Underdog-Bark-3.0`](https://huggingface.co/ConwayResearch/Underdog-Bark-3.0)
   and [`ConwayResearch/Underdog-Bark-3.0-Clean`](https://huggingface.co/ConwayResearch/Underdog-Bark-3.0-Clean)
   now render **"License: cc-by-nc-4.0"** in the card header, and their body
   text reads (Bark 3.0): "Licence CC BY-NC 4.0 (see `LICENSE`; commercial
   use: license@conway.tech); the original is CC-BY-4.0 and `NOTICE` lists
   the attribution." Clean's body has the equivalent sentence.
3. The [`FluidInference/bark-3.0-coreml`](https://huggingface.co/FluidInference/bark-3.0-coreml)
   card still renders **"License: cc-by-4.0"** and credits "Underdog Bark
   3.0 and Bark 3.0 Clean by Conway Research, CC-BY-4.0" — i.e. the
   downstream conversion repo has not (yet) followed the upstream change.
4. Independent trackers record a Conway-wide relicensing event: weights
   moved to CC-BY-NC-4.0 on **2026-11-05** with commercial use "by separate
   licence from license@conway.tech" (and describe the prior state
   variously as CC-BY-4.0 / Apache-2.0 depending on the model — treat the
   "before" label per-model, not fleet-wide). Buddadawg's local `NOTICE`
   files predate/are consistent with the pre-change state.
5. CC-BY-4.0 and CC-BY-NC-4.0 grants are **irrevocable for copies already
   received** under them (CC 4.0 §2(a)(1), §6). A licensor may stop
   offering the work under CC-BY and offer new copies under CC-BY-NC, but
   cannot retroactively convert a CC-BY copy someone already lawfully
   holds into an NC copy. Which grant covers *Buddadawg's redistribution
   of copies it fetched earlier*, and copies *users fetch after the
   change* via `fetch_models.sh`, are different questions — and NC's
   "primarily intended for or directed towards commercial advantage"
   test makes a paid app the clear case and a free app from a
   commercial entity the grey case.

That is the ambiguity: **the bytes are the same; the grant attached to
new downloads appears to have narrowed on 2026-11-05, while every
artefact Buddadawg actually bundles still says CC-BY.** Do not resolve
this by picking the friendlier label. Resolve it in writing.

## 2. Distribution decision: bundled 646 MB vs first-run download

Today: everything bundled. `bundle.sh` copies `Models/` (ANE subset,
199 MB in the app) and `ModelsClean/` (427 MB) into
`Contents/Resources/`; the app needs no network ever. `fetch_models.sh`
is a *developer/build-time* download, not a user-facing one.

| Attribute | A. Bundle both engines (status quo, 646 MB) | B. Bundle Clean only (~447 MB) | C. Thin app (~20–25 MB) + first-run model download |
| --- | --- | --- | --- |
| Download / update size | 646 MB first download; later code-only fixes stay small via Sparkle binary deltas because the 97%-of-bytes weights rarely change (see §5 — verify the real delta) | ~447 MB | ~25 MB app + 427 MB (Clean) once; verbatim fallback +199 MB only if fetched |
| Offline first run | Yes | Yes | No — needs network + progress UI + failure handling |
| Notarisation / signing | Weights sealed inside the signed bundle: tamper-evident, Gatekeeper story simple | Same | Downloaded weights live outside the seal (e.g. `~/Library/Application Support/Buddadawg/`): must self-verify SHA-256 before loading, must never load code from there (weights are data, `.mlmodelc` contains `model.mil` — treat as data, but document it) |
| Licence exposure | Buddadawg *redistributes* the weights with every download — needs the redistribution right (§1.1 Q3a) | Same, fewer weights | User's app fetches from the licensor's (or converter's) host — redistribution argument is weaker/thinner, but Buddadawg still *causes* the copy; Q3b still needed. Do not treat C as a licence loophole |
| Hosting cost / reliability | GitHub Release asset (2 GB limit per file — 646 MB fits; bandwidth is GitHub's) or own CDN | Same | Depends on Hugging Face availability + pinned revision surviving; HF rate-limits/renames become your outage |
| Homebrew cask | Large but acceptable; cask just points at the release `.dmg`/`.zip` | Same | Cask installs a shell that fails offline — reviewers dislike "app does nothing until it phones a third party"; also complicates `zap`/uninstall (downloaded models must be in `zap` trash paths) |
| Private-beta simplicity | One file, no downloader to write or secure | One file, drops the `engine=bark` escape hatch (or makes it download-on-demand) | Most engineering: resumable download, checksum, disk-space check, cancel/retry, mirror fallback |
| Fallback engine | Verbatim Bark available instantly if Clean fails to load (`main.swift` already falls back) | Loses instant fallback; Clean load failure = dead app | Fallback can be lazy-fetched on first Clean failure |

**Recommendation: A for private beta and first public release; design C
as the 1.x optimisation, not a launch blocker.** Rationale: the product
promise is literally "no network at runtime (models are bundled)"
(`README.md`), the fallback path already depends on both engines being
present, and a model downloader is the single largest new attack/bug
surface (partial files, wrong revision, MITM if checksums are skipped).
646 MB is unremarkable for a local-AI app in 2026. Revisit C when update
cadence makes full downloads painful — and note Sparkle binary deltas
(§5) already blunt that pain because unchanged weight files delta to
~nothing.

If/when C is built, non-negotiables:

- Pin **exact Hugging Face commit hashes**, never `resolve/main`
  (`fetch_models.sh` currently uses `resolve/main` — fine for a dev
  script, unacceptable for a shipped downloader). Pin both the Conway
  verbatim files and the FluidInference Clean files.
- Publish a signed `models-manifest.json` (per-file URL, byte size,
  SHA-256) inside the app bundle (therefore inside the notarised seal);
  verify every file after download and again if size/mtime changed.
  The current `fetch_models.sh` verifies nothing — even for the dev
  script, adding `shasum -a 256 -c` against a committed manifest is a
  cheap pre-release fix worth doing regardless of A vs C.
- Download over HTTPS only, to a temp file, atomic rename on success,
  resume support (`URLSession` download task), free-disk check
  (need ≥ ~1.3 GB transient for both engines), and a "models are
  downloaded from Hugging Face (Conway Research / Fluid Inference)"
  disclosure with the licence shown *before* download.
- Keep `--precompile` semantics: after download, run the same warm-up
  transcription so ANE compilation happens during onboarding (§4), not
  on first fn press.

Also decide the artefact: `.dmg` (signed + notarised + stapled; best
drag-install UX) as primary, `.zip` of the `.app` as the Homebrew/Sparkle
artefact. Both from the same `build/Buddadawg.app`. Never ship the
current `install.sh` build-from-source flow as the user install path —
keep it as the documented "build it yourself" route.

## 3. Signing and notarisation checklist

Current `bundle.sh` self-signing is a *local TCC-stability hack*, and it
is the correct hack for development. It is not distributable: Gatekeeper
rejects it on any other Mac (`spctl` above). Public distribution outside
the Mac App Store requires Developer ID + hardened runtime +
notarisation; since macOS 10.15 an unnotarised Developer ID app is
blocked by default, and there is no "right-click → Open" story to rely
on in 2026 documentation.

This app's sensitivity: it creates a **listen-only `CGEvent` session tap**
(`Hotkey.install()`, `.cgSessionEventTap`, flagsChanged + keyDown),
posts a synthetic ⌘V (`Paster`), reads the microphone, and registers a
login item (`SMAppService`). None of that needs a special entitlement
for Developer ID distribution — Accessibility (TCC) consent is the gate,
not an entitlement — but all of it makes *identity continuity* critical:
macOS keys TCC grants to the code identity (bundle id + Team ID +
designated requirement). Changing identity later re-prompts every user.

Checklist (in order; each step is a release-script change, not an app
behaviour change):

- [ ] Enrol in the Apple Developer Program ($99/yr) under the name that
      should appear as the signer. **Decide individual vs organisation
      now** — the Team ID is forever for TCC/Sparkle continuity purposes.
      Changing teams later = new identity = all users re-grant
      Accessibility + mic, and Sparkle designated-requirement continuity
      breaks.
- [ ] Create a **Developer ID Application** certificate (+ Developer ID
      Installer only if shipping a `.pkg`, which this plan does not).
      Store the `.p12` + password in the CI secret store / password
      manager, never in git. `security find-identity -v` must list it.
- [ ] Freeze the bundle id `co.alex.buddadawg` (already in `bundle.sh`
      and in the README's `defaults write` instructions). Renaming it
      post-beta resets TCC, `UserDefaults` (recents, `engine`, `units`),
      the login item, and `~/Library/Logs/Buddadawg.log` continuity.
- [ ] Add an `Entitlements.plist` for the release build. Start from
      **hardened runtime with zero exceptions**
      (`codesign --options runtime --timestamp`). Test before adding
      anything: Core ML/ANE, Metal overlay, `AVAudioEngine`, event tap,
      and `MediaRemote` use in `MediaPauser` should all work without
      `allow-jit`/`allow-unsigned-executable-memory`/
      `disable-library-validation`. Only add an exception with a
      comment naming the observed failure it fixes — notarisation
      allows several exceptions, but each one is attack surface a
      reviewer (and Homebrew audit) will ask about. Specifically
      verify: no `com.apple.security.get-task-allow` in release
      (notarisation rejects debugging entitlements in practice and it
      must never ship).
- [ ] Sign **inside-out, no `--deep`** (Apple explicitly deprecates
      `--deep` for distribution; current `bundle.sh` uses
      `--force --deep` with the self-signed cert — fine locally, must
      change for release): sign any nested code first (today there is
      no nested framework/helper — FluidAudio is statically linked,
      confirmed by `otool -L` showing only system libraries — so the
      practical sequence is: sign the main executable with
      entitlements, then the `.app`; when Sparkle is added, its
      `Sparkle.framework` + `Autoupdate`/`Updater.app` helpers must be
      signed before the outer app, per Sparkle's docs).
- [ ] Keep a **stable designated requirement**. With Developer ID the
      default DR (bundle id + Apple-anchored Developer ID leaf for the
      Team) is already stable across rebuilds — do *not* carry over the
      `-r="…certificate leaf = H\"…\""` self-signed pin. Verify with
      `codesign -dr - Buddadawg.app` and record the DR in the release
      notes; Sparkle and TCC both depend on it not drifting.
- [ ] `Info.plist` hardening in the *release* generation (still
      generated by script — keep single source of truth): add app icon
      (`CFBundleIconFile` + asset), `NSHumanReadableCopyright`,
      `CFBundleDevelopmentRegion`, and (with Sparkle, §5) `SUFeedURL` +
      `SUPublicEDKey`. Keep `LSUIElement=true` and the existing
      `NSMicrophoneUsageDescription` wording ("listens only while you
      hold fn") — it is accurate; do not weaken it. Bump
      `CFBundleVersion` on *every* shipped build (Sparkle and
      `SMAppService` both care).
- [ ] Notarise: zip/dmg the signed app →
      `xcrun notarytool submit … --wait` (App Store Connect API key
      `.p8` preferred for CI; Apple ID + app-specific password works
      locally) → `xcrun stapler staple Buddadawg.app` (and the `.dmg`)
      → `xcrun stapler validate`. Gate checks on a clean machine/VM:
      `spctl -a -vvv --type execute` → `accepted, source=Notarized
      Developer ID`; `codesign --verify --strict --verbose=4`.
- [ ] First-launch TCC test on a machine that has never seen the
      self-signed build: mic prompt fires once, Accessibility prompt
      (`AXIsProcessTrustedWithOptions` with prompt, already in
      `main.swift`) lands the user in the right Settings pane, grants
      survive an update (same Team ID/DR), and `tccutil reset` recovery
      is documented (§4). Note: users migrating from the self-signed
      build *will* re-grant once — say so in the beta notes.
- [ ] Decide **App Sandbox: no**. A sandboxed Mac App Store build
      cannot do a global listen-only event tap + synthetic paste into
      other apps the way Buddadawg does; Developer ID products are not
      required to be sandboxed. State this explicitly in the FAQ so
      "why not the App Store?" has a one-line answer. (Revisit only if
      Apple ships a dictation-input API that replaces the tap.)
- [ ] Release-script hygiene: separate `scripts/bundle.sh` (local dev,
      self-signed, keep as-is) from a new release path (Developer ID)
      rather than forking behaviour on env vars inside one script —
      or, if one script, make the identity an explicit required
      argument so a release can never silently fall back to the
      self-signed cert. The current auto-create-a-cert-with-password-
      `bark` block must never run in CI.
- [ ] Keep `scripts/install.sh`'s `pkill`/`rm -rf /Applications/…`
      behaviour out of any user-facing installer; the shipped artefact
      is drag-install. `install.sh` remains the from-source path.

Cost/time reality: enrolment approval can take hours–days; first
notarisation of a 646 MB app uploads the whole thing (budget the
upload + Apple's scan, typically minutes, occasionally much longer).
Do the first notarisation well before the beta date (§9).

## 4. First-run onboarding (mic + Accessibility + ANE compile)

Today's first run (from `main.swift`): requests mic access, prompts for
Accessibility, installs the tap (fails → status "Allow Accessibility,
then relaunch"), registers launch-at-login by default (once, via
`loginItemConfigured`), seeds the dictionary, then loads the model with
status text "Loading model…" → after 3 s "Preparing model (one-time, a
minute or so)…". `scripts/install.sh` hides the worst wait by running
`--precompile` before first `open`. A downloaded `.dmg` gets none of
that cover — onboarding must own all three waits explicitly.

Required flow for public beta (menu-bar app, `LSUIElement` — so the
"window" is a small welcome panel the app shows itself, plus the status
menu; there is no main window to hide this in):

1. **Welcome / what-permissions-why** (before any system prompt):
   one screen, three bullets in plain language: Microphone (only while
   fn is held; audio never leaves the Mac), Accessibility (to hear the
   fn key in any app and paste the result; keystrokes are not recorded
   or sent anywhere), and a one-time model preparation step. Link the
   privacy section (§6). Never fire the mic and Accessibility prompts
   simultaneously on first launch — stage them: explain → mic →
   explain → Accessibility with a button that triggers the existing
   `AXIsProcessTrustedWithOptions(prompt)` call and a deep link to
   `x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility`.
2. **Accessibility grant loop**: poll `AXIsProcessTrusted()` (the app
   already logs it at launch) and update the panel live when the user
   flips the toggle; auto-retry `hotkey.install()` on grant instead of
   requiring relaunch where possible. Keep the current fallback status
   text for the menu. Handle the classic failure — user granted a
   *stale* (self-signed/old) Buddadawg entry — with "remove the old
   Buddadawg row with −, then re-add" instructions + `tccutil reset
   Accessibility co.alex.buddadawg` as the documented last resort.
3. **ANE compile / model preparation progress**: Core ML compilation
   for the Neural Engine is the "~5 minute wait" `install.sh` warns
   about and the README softens to "a minute or two" — measure on the
   slowest supported machine (base M1) and publish the real number.
   During onboarding show determinate-as-possible progress: "Preparing
   speech model for your Mac (one time)…" with elapsed time, engine
   name, and a guarantee the panel can be closed and preparation
   continues (status menu mirrors it). Reuse the existing warm-up
   (1 s of silence through the loaded transcriber) as the "done"
   proof, then flip to "Ready: hold fn and talk" and offer a **test
   dictation** into a scratch field inside the panel so the first
   success doesn't depend on some other app's text field.
4. **fn-key education**: hold vs double-tap-to-lock vs fn+key cancels,
   the bottom-edge glow states (`--demo` already loops them — reuse
   that loop in onboarding), "transcript stays on your clipboard",
   Recent Dictations, Edit Dictionary. One screen, skippable,
   re-openable from the menu ("Show Welcome / Test Dictation").
5. **Login item**: today it defaults **on** silently. For a public
   release, surface it on the welcome screen as a pre-ticked-but-visible
   checkbox ("Launch at login — recommended for a dictation key") so
   the consent is informed; keep the menu toggle. This is a behaviour
   *presentation* change to agree with the app lane, flagged not
   assumed (this plan makes no code edits).
6. **Failure states with exits**: mic denied (deep link to Privacy →
   Microphone + "Buddadawg can't work without this"), no input device
   / silent capture (the app already detects held-but-no-audio and
   says "check your mic input" — mirror that in the test-dictation
   step), Clean model failed → verbatim fallback engaged (already
   automatic; onboarding should *name* it: "Ready (Bark fallback)"),
   low disk (only relevant under distribution option C).
7. **No account, no email gate, no telemetry opt-in buried here.**
   If crash reporting is ever added (§6), its consent is a separate,
   off-by-default toggle — never a pre-ticked onboarding checkbox.

Acceptance test: fresh macOS user account, no prior TCC grants, wall
clock from first `open` to successful test dictation recorded for the
benchmark page (§10). Do this on current macOS and on macOS 15 (the
`LSMinimumSystemVersion` floor).

## 5. Auto-update approach

**Sparkle 2** is the standard for Developer ID Mac apps and the
recommendation here. Mechanics that matter for Buddadawg:

- Updates described by a signed **appcast** (RSS/XML) hosted over HTTPS
  (GitHub Releases / Pages is fine); each update archive is verified
  with an **EdDSA (Ed25519)** signature (`SUPublicEDKey` in
  `Info.plist`, private key generated by Sparkle's `generate_keys`,
  kept in the maintainer keychain/CI secret — losing it means users
  must manually reinstall, so back it up like the Developer ID cert).
  Sparkle additionally checks Apple code-signing continuity (same Team
  / designated requirement) before installing.
- The app must be Developer ID-signed *including Sparkle's nested
  framework and helper apps* (§3 inside-out signing) and notarised as a
  whole. Do not attempt Sparkle on the self-signed build.
- **Delta updates**: Sparkle generates binary deltas between versions
  (`generate_appcast` does this automatically for recent versions).
  With 626 MB of mostly-unchanging weights, a code-only fix should
  delta to a few MB — verify and publish the real delta size; this is
  what makes distribution option A (§2) sustainable.
- UX for a menu-bar agent: `SPUStandardUpdaterController` with a
  "Check for Updates…" menu item, automatic background checks on
  (daily), download in background, install on quit/relaunch prompt.
  Never interrupt a recording/transcription to nag about an update.
  Show release notes (HTML from the appcast) — keep them short and
  honest, including permission/model changes.
- Channels: one production appcast for public beta; a separate beta
  appcast (`SUFeedURL` override via defaults for testers) only if the
  cohort in §9 needs pre-releases. Do not ship `@beta` complexity on
  day one if the cohort is small enough for manual builds.
- Rollback story: keep the previous notarised build downloadable;
  document `defaults write co.alex.buddadawg engine bark` (already in
  README) as the engine escape hatch — distinct from an app rollback.
- Model-only updates (new Clean checkpoint, same app): under option A
  they ship as a normal app update (large delta, infrequent). Under a
  future option C they could ship via the signed model manifest
  without an app update — another reason C is a 1.x topic, with its
  own signing design, not a Sparkle setting.
- Homebrew cask users update via `brew upgrade` — Sparkle must detect
  a cask-managed install or at least not fight it (standard practice:
  still check, but cask `auto_updates` stanza guidance applies; decide
  and document one owner of updates to avoid double-updaters).

Alternatives considered and rejected for launch: hand-rolled updater
(reinventing signature verification is how supply-chain bugs happen),
Mac App Store (sandbox blocks the core interaction, §3), "check the
GitHub releases page" (fine for private beta, not for public).

## 6. Privacy posture

The honest headline is already true and must stay provably true:
**audio and transcripts are processed on-device; Buddadawg has no
server.** The release work is turning that claim into checkable facts.

What exists today (code-read, not marketing):

- No account, no API keys, no analytics SDK. Runtime model loading is
  local (`loadLocal`); the only network code paths in the shipped
  binary are unused FluidAudio internals + future Sparkle. **Before
  launch**: run the release build behind a firewall/Little Snitch-style
  log through a full dictation cycle and publish the result ("zero
  connections during recording/transcription; update check only to
  <appcast host>") on the privacy page. Re-run per release.
- **Recents**: last 8 transcripts in `UserDefaults` under
  `recentDictations` (deduplicated, newest first; "Clear Recents" in
  the submenu). Plaintext, per-user, synced nowhere — but `UserDefaults`
  is readable by anything running as the user and lands in backups.
  Document exactly this, including how to wipe
  (`defaults delete co.alex.buddadawg recentDictations` + Clear
  Recents). Consider (app-lane decision, not this plan's edit): a
  "don't keep recents" toggle for shared/high-sensitivity machines.
  Verified live on this machine: `defaults read co.alex.buddadawg`
  shows the 8 stored transcripts — treat screenshots of that as
  sensitive in bug reports (§7 templates warn about it).
- **Clipboard-stays-paste**: by design the transcript (+ trailing
  space) remains on `NSPasteboard.general` after the synthetic ⌘V so
  the user can re-paste. Consequence that must be disclosed: **any
  clipboard manager (Maccy, Paste, Raycast history, etc.) and any app
  polling the pasteboard will see and may retain dictated text**, and
  Universal Clipboard may carry it to other Apple devices. Buddadawg
  currently sets a plain `.string` type with no transient/concealed
  markers. Document this prominently; evaluate (app lane) adding the
  conventional `org.nspasteboard.TransientType` /
  `org.nspasteboard.ConcealedType` markers as an *option* — noting the
  trade-off: marking concealed breaks the "⌘V re-sends it anywhere"
  feature with managers that honour the markers, so default stays
  clipboard-stays, option is for sensitive contexts. Never silently
  change this behaviour in an update.
- **Logs**: `~/Library/Logs/Buddadawg.log` records timings, char
  counts, audio levels, device names — code comment and observed
  content agree it never logs transcript text. Keep that invariant as
  a review rule ("no transcript, no audio, no dictionary contents in
  logs"); logs are still mildly sensitive (dictation times/lengths) —
  say so, and gate any "attach logs" bug-report flow behind the user
  reading them first.
- **Dictionary**: `~/.config/buddadawg/dictionary` is plaintext
  user data (names/jargon corrections). Local only; mention in the
  data inventory.
- **Media pause**: pauses/resumes other apps' playback via
  MediaRemote. No content is read or stored; the log lines include
  playing-app bundle ids/PIDs (observed in the local log) — include
  in the inventory so "what's in the log" has no surprises.
- **Model download** (build-time today; first-run under option C):
  Hugging Face sees the downloader's IP like any HTTPS fetch. Under
  option A this applies only to from-source builders. Sparkle's
  appcast host sees update checks (IP + version) — disclose host and
  frequency; Sparkle itself collects nothing.

Deliverables: a `PRIVACY.md` (repo) + privacy section on the site/
README with a **data inventory table** (data, where stored, leaves
device?, how to delete) covering: microphone audio (RAM only,
discarded after transcription), transcripts (clipboard + optional
recents), dictionary file, log file, preferences (`engine`, `units`,
`loginItemConfigured`, media-pause toggle), Application Support cache
(compiled-model cache dir created in `main.swift`). Plus an explicit
"no servers, no accounts, no sale/sharing, no training on your audio"
statement. If crash reports are ever wanted: opt-in, user-sent
(Apple's "share with developers" or a manual attach-logs flow) —
no third-party crash SDK by default in an app whose pitch is privacy.

GDPR/CCPA note for the free release: with no servers and no personal
data collection by the developer, obligations are minimal — but the
privacy page is still required by Homebrew/user expectation, and the
moment a website, mailing list, or paid checkout exists (§11), that
changes. Get the page reviewed when the paid question opens, not now.

## 8. Homebrew cask (after notarisation, not before)

Homebrew is a *second* channel, sequenced after direct download works:

- The official `homebrew/cask` tap now requires casks to pass
  Gatekeeper: apps must be Developer ID-signed and notarised
  (Homebrew 5.0, Nov 2025 deprecated unsigned/unnotarised casks in
  the official tap, with removal from Sep 2026; `brew audit` checks
  signing/notarisation, and Acceptable Casks requires artefacts to
  pass Homebrew's Gatekeeper checks without SIP/Gatekeeper bypass).
  The current self-signed build is ineligible, full stop. A *custom
  tap* (`brew tap alx8g/buddadawg`) is not bound by official-tap
  notability/notarisation policy and is the right beta channel if
  one is wanted before the official submission.
- Official-tap notability: new casks need demonstrated interest
  (commonly cited thresholds: 30 forks / 30 watchers / 75 stars,
  tripled for self-submissions; repos <30 days old ineligible).
  Plan on custom tap first; submit officially once the public beta
  (§9) clears the bar organically. Do not astroturf stars.
- Cask shape: `cask "buddadawg"` pointing at the versioned GitHub
  Release `.zip`/`.dmg` with `sha256`, `depends_on macos: ">= :sequoia"`
  (macOS 15) + `depends_on arch: :arm64`, `auto_updates true` if
  Sparkle owns updates (§5 — pick one owner), `zap` covering
  `~/Library/Logs/Buddadawg.log`, Application Support cache,
  `~/.config/buddadawg`, and the `co.alex.buddadawg` defaults
  domain. First-run still needs the §4 onboarding (cask cannot grant
  TCC) — `caveats` must say "open Buddadawg once and allow Microphone

- Keep the cask file in its own tap repo (or the official tap PR);

## 9. Beta cohort plan

Goal: find hardware/TCC/app-compatibility breakage, not growth.

- **Private beta (10–25 people, 2–3 weeks minimum).** Recruit for
  *coverage*, not enthusiasm: base M1 (slowest ANE compile), M2/M3/M4
  spread, macOS 15 + current macOS, external/USB/Bluetooth mics,
  users of clipboard managers, users whose daily apps include the
  paste-hostile ones (terminals, Electron apps, remote-desktop/VMs,
  password fields), at least a few non-developers. Distribute the
  notarised `.dmg` via an unlisted GitHub pre-release. Each tester
  gets: install + onboarding, a 5-minute task script (dictate a
  paragraph with numbers/times/names into 3 different apps; trigger a
  cancel; use double-tap lock for a long dictation; recover a missed
  paste via Recents + ⌘V), and a feedback form (what broke, target
  app, engine shown, verbatim status text). Explicitly tell testers:
  recents/clipboard contain what you dictate — don't dictate secrets
  during the beta; logs are safe to share after a skim (§6).
- **Exit criteria for private beta**: zero "cannot grant
  Accessibility / cannot dictate at all" reports unresolved; ANE
  first-prepare time measured on base M1 and quoted in onboarding;
  paste success/failure table by target-app category started (§10);
  no crash that loses a dictation without Recents saving it.
- **Public beta (GitHub Release marked pre-release + README badge).**
  Open issues with §7 templates, Discussions for support. Ship at
  most weekly; every build notarised (no unsigned "nightly" side
  channel — it trains users to bypass Gatekeeper and poisons TCC
  identity). Announce in one or two relevant communities with the
  honest one-liner: hold-fn, on-device, free/OSS, Apple silicon only,
  English only (Bark 3.0 is English-only per its card — do not let
  Parakeet's 25-language reputation imply otherwise).
- **Support load planning**: solo-maintainer reality — publish a
  troubleshooting page *before* announcing (Accessibility stale-entry
  fix, mic-input selection, `engine=bark` escape hatch, how to fully
  uninstall incl. login item + defaults + dictionary). Most dictation-
  app support is TCC and mic routing; pre-answer it.

## 10. Benchmark publication plan (operational, not just WER)

Conway already publishes Open ASR Leaderboard-style WER for Bark 3.0
(company-run, "not on the leaderboard yet" per the card — cite it as
such, never as independent). Buddadawg's credibility contribution is
**end-to-end dictation behaviour on real Macs**, via the existing
`BarkBench` (verbatim, `Models`) and `CleanBench` (`ModelsClean`)
harnesses plus app instrumentation that already logs per-dictation
timings ("transcribed N chars in M ms").

Publish (as `docs/benchmarks.md`, versioned per release, with raw
clips/scripts where licences allow):

- **Methodology first**: machine(s) (chip, RAM, macOS build), clip
  set provenance (use openly licensed speech — e.g. LibriSpeech/
  Earnings-style sets — or self-recorded consented clips; never
  publish beta testers' audio), exact commands
  (`.build/release/CleanBench ModelsClean clip.wav`), warm vs cold,
  number of runs, what's included in each timing.
- **Accuracy**: WER for verbatim Bark; for Clean, report WER *and*
  disfluency-removal behaviour separately (Clean intentionally deletes
  "um"/false starts, so naive WER against a verbatim reference
  punishes the feature) — include a small hand-scored
  "dictation-intent" set (numbers→digits, times, names/jargon with
  dictionary on/off, punctuation/casing) scored as
  exact-after-formatting (`DictationFormatter` is part of the product;
  benchmark the pipeline, not just the checkpoint).
- **Operational metrics** (the numbers dicta­tion users feel):
  fn-release→paste latency p50/p95 by audio length (5 s / 30 s / 120 s,
  incl. segmentation behaviour past 15 s windows), cold-start model
  load + first-ever ANE compile wall-clock per chip, steady-state
  memory (binary + loaded models) and idle CPU (must be ~0 — a
  menu-bar agent that burns CPU is a bug), energy impact per minute
  dictated if measurable, long-dictation behaviour (5 min locked
  recording: memory growth, cut quality), cancel latency, media
  pause/resume success rate by player app, paste success by target
  app category (native/Electron/terminal/browser/VM).
- **Robustness table**: mic devices tested, noisy-environment clips,
  quiet/clipped speech (the recorder logs peak/clamped samples — use
  them), non-English speech (document failure mode honestly),
  proper-noun/dictionary examples.
- **Comparison honesty**: if comparing to system Dictation/Whisper/
  Parakeet-base, same clips, same machine, same scoring script,
  published alongside. No cherry-picked single clips. State clearly
  which numbers are Conway's, which are Buddadawg-measured.
- Cadence: rerun the core table on every model or FluidAudio version
  bump; date every table. A stale benchmark page is worse than none.

## 11. Paid version: separate blockers

Everything in §§2–10 is about a **free** release. A paid version
(one-time, subscription, or paid tier of the same app) additionally
hits:

| Blocker | Why it blocks paid specifically | Unblock |
| --- | --- | --- |
| Bark 3.0 + Clean under CC-BY-NC-4.0 (current card state) | NC forbids use "primarily intended for or directed towards commercial advantage or monetary compensation". Selling an app whose core feature is the NC model is the textbook case. The Parakeet base being CC-BY does not help while the shipped derivative is NC | Written commercial licence from Conway (§1.1 Q5) **or** swap engines to a commercially clear checkpoint (e.g. NVIDIA Parakeet / Moondream Ultra under CC-BY, or another permissively licensed model) and re-validate quality |
| FluidInference Clean conversion labelled CC-BY-4.0 | A downstream CC-BY label cannot grant commercial rights Conway didn't give; relying on it for a paid product is building on a likely-stale label (§1.1 Q6) | Same Conway licence must expressly cover the converted Core ML form, or convert a commercially licensed checkpoint |
| Tenor GIF / "butta dawg" branding | Tenor terms bar commercial purpose; the meme clip + name in paid marketing/store listing invites takedown and trademark trouble | Original mascot/name/assets for any commercial surface (keep the joke in the free README only if §1 row 11 is accepted — even there, owned art is cleaner) |
| Name/trademark clearance ("Buddadawg", "Bark") | Free OSS tolerates nominative use; a paid product needs its own registrable mark and must not imply Conway/Underdog endorsement | Trademark search + §1.1 Q8 answer |
| Commerce infrastructure | Paid direct download needs a merchant of record / tax handling (e.g. Paddle/Lemon Squeezy-class), licence-key/activation design (must not phone home in a way that breaks the privacy pitch — offline keys), refund/support obligations, consumer-law compliance (EU digital-goods rules) | Separate product/legal project; nothing in the current codebase anticipates it and nothing should be bolted on during the OSS launch |
| Business entity + Developer enrolment type | The Team ID decision in §3 interacts with whose name takes money; switching later breaks TCC/Sparkle continuity for *all* users, free included | Decide before first notarised public build, even if paid is hypothetical |
| Support/privacy surface | Paid users buy a support expectation; a paid privacy product will be (rightly) audited harder on clipboard/recents behaviour (§6) | Privacy page legal review; consider the concealed-clipboard + no-recents options as launch features of a paid build |

FluidAudio (Apache-2.0), NemoTextProcessing (Apache-2.0/MIT stack),
Parakeet base (CC-BY-4.0), Apple frameworks, and the app's own code
(once MIT/Apache-licensed by its author — the author can always
dual-license their own code) do **not** block a paid version. The
weights do. Do not announce pricing, a waitlist-for-paid, or "Pro"
teasers until the first table row is resolved.
